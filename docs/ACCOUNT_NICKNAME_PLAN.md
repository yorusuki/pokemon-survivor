# 暱稱修改與好友顯示方案（尚未實作）

## 目標與範圍

修改玩家公開暱稱，保留 UID、密碼／Google 身分、存檔、好友與冒險紀錄。建議將「登入帳號」與「公開暱稱」分開；密碼登入仍使用原帳號，不因改暱稱失去登入入口。介面應同時清楚標示兩者。

## 現況

- `users.login` 為密碼登入查詢鍵，`users.display_name` 為認證回應顯示名稱。
- `names` 保存唯一暱稱與 UID 的對照；目前政策不允許同一 UID 另占第二個名字。
- `profiles.name/lower`、存檔的 name、瀏覽器 `ps.nick.<uid>` 快取各有名稱；現有首次取名流程不能直接當作完整改名流程。
- 好友以兩個 UID 組成關係鍵，因此名稱更改不會切斷關係。但 `friendships.names` 保留建立時的名稱快照，離線好友也可能顯示舊名。
- 房間成員、合作角色、邀請與排行榜亦有名稱快照。presence 本身不保存名字，僅重新送心跳不能修正好友名稱。

## 建議流程

1. 在「設定 → 帳號」加入修改公開暱稱，顯示固定登入帳號與目前暱稱。輸入沿用目前的 Unicode 字母／數字／底線限制，伺服器統一驗證字元、長度與小寫鍵；不能只靠前端。
2. 以專用改名 API 處理登入狀態、代理驗證、CSRF、頻率限制與唯一性；在同一交易鎖定帳號與名稱保留，取得新名稱、更新公開名稱及存檔名稱、釋放舊名稱。失敗整筆回滾；不修改 UID 或 Google 對應。
3. 不開放一般 documents API 任意多占名稱或繞過改名冷卻。建議成功後 7 天才能再次改名；冷卻以伺服器時間持久保存。
4. 舊名可設 30 天不可被別人搶用的保留期，以降低冒名風險；搜尋舊名不自動指向新名，避免混淆。這需要名稱保留資料及到期處理。
5. 好友／邀請／公開 profile 以 UID 查詢最新名字；由伺服器批次投影名稱，避免逐好友重複查詢或每次改名重寫所有好友文件。畫面可短期顯示「原名 → 新名」，仍以 UID 確認邀請對象。
6. 首版限制回到主選單且不在房間內改名，避免進行中的合作角色與結算快照不一致。歷史戰績保留當時名稱，點開玩家資料時顯示目前暱稱。
7. 成功後更新認證／公開 profile、存檔與瀏覽器暱稱快取；多分頁及離線同步需採伺服器版本較新的名稱，避免舊存檔把暱稱改回。

## 影響區塊

| 區塊 | 需要的改動 | 影響 |
|---|---|---|
| `server/index.js`、`policy.js` | 專用改名交易、名稱投影、驗證與限流，阻止舊同步覆寫 | 中等，主要正確性風險 |
| `schema.sql`、資料存取 | 改名時間／名稱保留期限與索引，既有資料採相容預設 | 小型 schema migration，實作前需確認 |
| `js/core/backend.js`、帳號 UI | 改名請求、登入帳號／公開名區分、錯誤與冷卻提示 | 中等 |
| `js/net/social.js`、社交 UI | 好友、搜尋、邀請、profile 依 UID 取得目前名，清除暱稱快取 | 中等，不重建好友關係 |
| 存檔／合作／排行榜 | 名稱版本同步、房內限制及歷史快照規則 | 中等，不改戰鬥資料 |
| API、操作文件及測試 | 請求格式、Unicode 邊界、重名競爭、離線衝突與多分頁 | 必要 |

## 驗證與風險

涵蓋重名同時搶占、大小寫-only 改名、Unicode 小寫擴張／補充平面字、冷卻繞過、失敗回滾、跨帳號拒絕、舊登入帳號仍可用、Google-only、好友離線改名後的顯示、邀請與戰績、舊分頁同步。

整體為中型帳號功能，不需重建遊戲、UID 或好友表，但不宜只加一個輸入框。實作前須確認：登入帳號保持不變、改名冷卻及舊名保留政策。此文件不變更認證、資料庫或現有帳號。
